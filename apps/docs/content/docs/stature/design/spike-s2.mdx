title: "Spike S2: is non-uniform (per-axis) scaling achievable on Minecraft 26.3?"
---

**Verdict: yes, and the intended shapes need only the cheaper half of it.**

Read from the 26.3 sources this workspace builds against: the NeoForm `mergeWithSources` tree,
class-file major 69, the one with `EntitySpawnReason` and `EntityTypes`. Every claim below names the
file and line it came from.

> **Read this first.** The first pass at this document was wrong, and the way it was wrong is worth
> keeping. `.utils/mc.py jars` lists several Minecraft versions out of one cache and ranked a
> **1.21.1** tree first, so a whole afternoon of reading was done against the wrong version, and only
> a compile error (`MobSpawnType`, `EntityType.ZOMBIE`) caught it. The 1.21.1 and 26.3 trees agree
> about everything this spike cares about, which is why the conclusion survives, but the line
> numbers did not, and the renderer had changed shape completely. Pin the version by evidence, not by
> position in a list.

## The question splits in two, and the plan treats them as one

| | What it needs | Cost |
|---|---|---|
| **2a** width ≠ height | nothing new in the data model | one mixin on a `final` method |
| **2b** width ≠ depth (rectangular footprint) | a depth value the game has no field for | one mixin, one field, ~6 call sites |

**2a is already in vanilla's data model.** `EntityDimensions` carries `width` and `height`, and
`scale(float widthScaleFactor, float heightScaleFactor)` scales them independently
(`EntityDimensions.java:33`). `LivingEntity` calls the *one-argument* form:

```
LivingEntity.java:3913   public final EntityDimensions getDimensions(Pose pose) {
LivingEntity.java:3914       return pose == Pose.SLEEPING ? SLEEPING_DIMENSIONS
LivingEntity.java:3915                                    : this.getDefaultDimensions(pose).scale(this.getScale());
LivingEntity.java:3917   protected EntityDimensions getDefaultDimensions(Pose pose) {
LivingEntity.java:3918       return this.getType().getDimensions().scale(this.getAgeScale());
```

So the two non-uniform shapes Stature is meant to carry (0.55 × 1.71 and 0.63 × 2.10) are expressible
today: they need `scale(0.55f, 1.71f)` where the code passes one factor. What stops a subclass doing it is
that `getDimensions` is `final`, so it takes a mixin rather than an override. One method, not a
redesign.

**2b is the real work.** `EntityDimensions` is a record with no depth, and the box is square by
construction:

```
EntityDimensions.java:20   public AABB makeBoundingBox(double x, double y, double z) {
EntityDimensions.java:21       float w = this.width / 2.0F;
EntityDimensions.java:23       return new AABB(x - w, y, z - w, x + w, y + h, z + w);
```

One `w` for X and Z. Nothing below that cares: collision, movement, raycasts, suffocation and
pressure plates all read `getBoundingBox()`, and an `AABB` is happy to be rectangular.

## The seams, and there are fewer than the plan feared

| Seam | Where | Note |
|---|---|---|
| The box | `Entity.java:495` `protected AABB makeBoundingBox(Vec3 position)` | the only place a box is built from dimensions, and it has the entity in hand. The no-arg `makeBoundingBox()` at `:491` is `final` and delegates here, which is why this overload is the injection point |
| The dimensions | `LivingEntity.java:3913` `getDimensions(Pose)` | `final`; composes type × age × scale attribute |
| The refresh | `LivingEntity.java:1186` area, `tick` | `tick` compares `getScale()` against the applied value and calls `refreshDimensions()` when it moved |
| The render scale | `LivingEntityRenderer.java:87` | `float scale = state.scale; poseStack.scale(scale, scale, scale);` |
| The growth fudge | `Entity.java:3539-3563` | vanilla already pushes a growing entity into free space |

The fourth is vanilla's own behaviour rather than something to write: `refreshDimensions()` calls
`fudgePositionAfterSizeChange(oldDim)` when the entity grew. That is §14.5's "spatial obstruction and
kinetic displacement" already implemented, with three limits worth knowing:

- it is skipped entirely for players (`Entity.java:3534`, `!(this instanceof Player)`), so a growing
  player is exactly the case Stature still has to solve;
- it only runs when both dimensions are ≤ 4 blocks (`Entity.java:3528`);
- it only runs when the entity *grew* (`Entity.java:3533`).

## The free-space search already takes three sizes

```
CollisionGetter.java:155   default Optional<Vec3> findFreePosition(
                               @Nullable Entity source, VoxelShape allowedCenters, Vec3 preferredCenter,
                               double sizeX, double sizeY, double sizeZ)
```

Named `sizeX`, `sizeY`, `sizeZ` in 26.3, and vanilla passes `width` for both X and Z
(`Entity.java:3546` and `:3555`). The API that places a growing entity is already rectangular; only
`EntityDimensions` cannot say so.

## The pathfinder already models width and depth separately

```
NodeEvaluator.java:30   this.entityWidth = Mth.floor(entity.getBbWidth() + 1.0F);
NodeEvaluator.java:32   this.entityDepth = Mth.floor(entity.getBbWidth() + 1.0F);
```

Two fields, both fed from the width. Whoever wrote this expected a depth accessor to exist.

## The renderer is the thing that changed most, and it matters

26.3 does not render an entity, it renders a **state**: `EntityRenderer.extractRenderState(T, S,
float)` (`EntityRenderer.java:169`) fills it, and `submit(S, PoseStack, SubmitNodeCollector,
CameraRenderState)` (`EntityRenderer.java:105`) draws it. `LivingEntityRenderer.submit` scales at
line 87 from `state.scale`, which `extractRenderState` set from `entity.getScale()`
(`LivingEntityRenderer.java:271`).

Two consequences for §14.2's "render matrices" half:

- The per-axis factors have to **travel on the state**, because `submit` never sees the entity.
  `LivingEntityRenderState` has one `public float scale` (`LivingEntityRenderState.java:20`) and no
  room for three, so the state needs a field of its own, or a mixin-added one.
- There is no `MultiBufferSource` in the 26.3 render path any more; it is `SubmitNodeCollector`.
  Any plan text naming the old one is stale.

Measured, not estimated: `getBbWidth()` has **94 call sites in 50 files**. Almost all are per-mob

whole "the collision resolver and the pathfinder all assume a single uniform scale" risk from
§14.2, and it fits in one table.

## Three things the plan should be corrected on

1. **§14.2 is right about the attribute and wrong about the type.** `generic.scale` is one float, so
   the *attribute* is uniform, but `EntityDimensions` has carried width and height separately since
   long before 26.3, and the two-factor `scale` is public API. Nothing needs inventing for 2a.
2. **§14.5's command envelope cannot be enforced through the attribute.** `generic.scale` is a
   `RangedAttribute` with a hard minimum of `0.0625`, so `0.05 ≤ s ≤ 16.0` asks for a value vanilla
   will not store. Either the envelope becomes `0.0625`, or Stature carries values the attribute
   cannot, or the clamp is widened with a mixin. `sanitizeScale(float)` (`LivingEntity.java:586`) is
   a protected hook that returns its argument unchanged, which is where policy belongs.
3. **`fixed` dimensions are never scaled.** `EntityDimensions.scale` returns `this` when `fixed` is
   true, which covers sleeping (`LivingEntity.java:177` area) and dying players. Frames must decide
   whether that stays true.

Also worth recording: `Player.POSES` gives a player **five** frames (standing 0.6 × 1.8, crouching
0.6 × 1.5, swimming / fall-flying / spin-attack 0.6 × 0.6, sleeping and dying fixed), and
`getAgeScale()` is 0.5 for a baby (0.3 turtle, 0.45 camel, 0.6 armadillo). A frame composes with all
of them, so the final box is `frame × age × scale attribute × pose`.

## What the runtime spike confirms, and what it cannot

Source reading settles the shape of the answer, not the platform. The Spike S2 experiment was the
boot:

1. **Do the mixins apply at all in this toolchain?** Loom runs in no-remap mode on an unobfuscated
   26.x tree, and the workspace has no example of a mixin into a Minecraft class under Fabric: Armature
   has none, and Tenet's single accessor lives in `common`, built by ModDevGradle.
2. **Does a rectangular box survive a tick?** The arithmetic is arithmetic; that the movement path
   does not object is not.

What it cannot decide: whether the numbers are good, saving and syncing a rectangular footprint, the
frame registry, NeoForge, or the client half (the self-test runs headless on a dedicated server, so
the render mixins are compile-verified only until someone runs `runClient` and looks).
